# GRID Autosport OpenXR bridge

The x86 bridge uses the Steam AVX renderer from build 4011980. The game draws the scene twice into its existing undistorted eye target. At the native frame boundary, the bridge copies that target once and uses the two game-provided rectangles for capture and OpenXR projection.

For normal play, connect the headset and choose **Launch VR** in the Autosport launcher. The launcher checks the 32-bit runtime, starts the registered Steam game and restores the stock executable when play ends. The portable launcher expects `renderer/gasxr.dll` and `probe/AutosportXRProbe.exe` beside it. Normal-session bridge and supervisor logs are under `%LOCALAPPDATA%\GRIDAutosportVR\sessions`. If a session is interrupted, close the game and reopen the launcher to recover the installation.

With MSVC 2022 and a local Khronos OpenXR-SDK checkout, build from the project root:

```powershell
cmake -S bridge -B artifacts/bridge-build -G "Visual Studio 17 2022" -A Win32 -DOPENXR_SDK=<path to your OpenXR-SDK checkout>
cmake --build artifacts/bridge-build --config Release --target gasxr -- /m:1
```

Close Autosport and leave Steam signed in. The benchmark runner uses the local Steam installation on E: and requires Python with psutil. For a reference pair with 64 mm eye separation:

```powershell
python bridge/run.py --mode capture --race-seconds 90
```

For headset projection, connect the headset to its 32-bit OpenXR runtime before launch:

```powershell
python bridge/run.py --mode openxr --race-seconds 90
```

The runner creates a hash-verified AVX backup, temporarily changes one D3D11 import name, and starts the registered game through Steam. Each run writes its images, native frame metadata and log under `artifacts/bridge-runs`. The log ties the capture to the game's benchmark frame and time. The San Francisco fixture cycles cameras. Race second 90 produced the driver cockpit in the reference run.

In headset mode, startup and the game's loading state use a level screen anchored in the seated space, `-gasvrscreendistance` centimetres ahead (150–600; 200 without it, the launcher passes 300) and at most 2.4 × 1.8 m at any distance. The game renders those frames with a centred field of view of at least 16:9 (the headset's own is nearly square, which cut the sides off widescreen layouts), and the screen shows them at that aspect. With `-gasvrintro3d=1` the pre-race intro shots stay in stereo instead and the FE manager's three non-HUD passes (RVA 1B7B63, 1B7B98, 1B7C09) are skipped for them, which removes the broadcast info panel and wipes; the pre-race intro ends once the car camera has been live for five seconds in a row (the game cuts to it briefly at scene start and between shots), and later shots such as finish cameras use the screen as before. When loading ends, the bridge hides the game's “SUNDAY / RACE 1/1” intro card. The pre-race intro shots (and any other shot that is not the player's car camera, such as finish cameras) are a 2D broadcast layout with an info panel and wipes, so headset play shows them on the seated screen and switches to stereo when the car camera is live: the vehicle view manager's byte +0x834 is set while it is, sampled once per native frame from the manager the race-start view request uses. The in-race pause menu is laid out for the whole flat frame, so in stereo it was head-locked and ran past the bottom of the field of view; headset play shows it on the seated screen too, with the centred loading field of view, while the game's pause flag (byte +0x1301 of the service the pause state sets at RVA 255EA6 and clears at 26AD11) is set. The bridge records that service in the pause entry's call at RVA 255EB2. The native fades and the rest of the frontend continue drawing. **HUD follows view** (Graphics → VR HUD) controls the race HUD for the next run. The default holds it ahead of the recentered seat, at `-gasvrhuddistance` centimetres (100–2000, default 100; the HUD keeps its angular size). Enabling it uses the game's original head-relative HUD.

`-gasvrhudparts=MASK` (1 entire HUD, 2 dial, 4 minimap, 8 counters, 16 position info) replaces the profile's HUD options for the session. The OSD manager's per-player setup (RVA 149480) reads them as `entire_OSD` (through RVA 2C1250, called at 14949B) and `dial_OSD`, `minimap_OSD`, `counters_OSD`, `positions_OSD` (through the settings lookup RVA 9F0F90 at 1494E8, 149538, 149586 and 1495D1); the bridge answers those five reads and never writes the profile. Without the argument the game decides, as before.

To check both HUD modes and the track reveal without a headset, run `python bridge/run.py --mode capture --compare-hud --race-seconds 8`. It captures both eyes at a fixed head tilt and closes the benchmark after sampling the race HUD. Add `--compare-slate` for a control run that shows the original intro card and captures the underlying scene on the next frame.

To reproduce an early window close with a connected headset, run `python bridge/run.py --mode openxr --quit-after-capture --race-seconds 1`. Success requires a stereo capture, clean process exits, stock restoration, and a completed OpenXR shutdown handshake. Omit `--quit-after-capture` for a full lap. The full run also requires the game's result XML to match the fixture. It saves that result alongside the eye capture.

Normal play can be checked without a headset on the [xr-sim](https://github.com/phunkaeg/xr-sim) OpenXR runtime: build it for x86 in `.deps/xr-sim` (`cmake --preset x86`, `cmake --build --preset x86-release`), then run `python capture/xrsim_play.py --seconds 50`. It starts the AVX game directly with a normal-play token, so the startup videos and title scene run, and models Virtual Desktop dropping focus (`focus policy vdxr-layers`, `shouldRender` held false, ~87 ms frames). It passes when the session is FOCUSED again; `--no-focus-loss` leaves the focus model alone. Results and xr-sim captures go under `artifacts/bridge-runs`.

Virtual Desktop holds `shouldRender` false while a session is not focused and restores focus only after frames that carry a layer. The bridge therefore keeps submitting while `shouldRender` is false, and on the first FOCUSED it re-places the seated screen and recenters once.

While its window is inactive the game pauses its startup videos and drops to about 18 fps, and a headset player rarely has that window focused. Bridge sessions (headset play and the capture benchmark) therefore withhold `WM_ACTIVATEAPP`/`WM_ACTIVATE` deactivations and `WM_KILLFOCUS` from the game; `-gasvrkeepactive=0` opts out. `--deactivate-at 2` (with `--no-keep-active` for the control) posts a deactivation to the game window to check this without touching the desktop focus.

The startup videos (`intel_sting.bk2`, `sting.bk2`) are drawn into the game's back buffer, not the HMD eye texture, which stays a flat dark fill. Until the first loading state of normal play, the seated screen therefore shows the back buffer, and the desktop mirror leaves it as the game drew it; `-gasvrstartupsource=eye` restores the eye-texture source. `capture/xrsim_play.py --shots 3,5,8,11` captures that interval.

Skip intro / logos (`-gasvrskipintro=1`, the launcher's Settings option, as GRID2VR): the two startup movies, `video\intel_sting.bk2` and `video\sting.bk2` in the game folder, are moved to their last frame at their first `BinkWait` (import hook), so each ends at once and the game continues as after a played movie; every other video plays. The game ships the same `bink2w32.dll` as GRID 2 (SHA-256 03f9c695...), so the seek is GRID2VR's: pending async decodes are completed first (`BinkDoFrameAsyncWait`; `BinkGoto` refuses pending jobs at +0x110 / +0x114), then `BinkGoto` to the last frame, checked by reading the frame back. The bridge log names each skipped movie.

Eye colour (`Bridge::eyeFormat`, as GRID2VR): the game's final picture holds display-encoded colour in a UNORM texture (the back buffer is `R10G10B10A2_UNORM`). OpenXR runtimes read a non-sRGB swapchain as linear light and encode it again, which washed the picture out. The eye images now use an sRGB swapchain: an 8-bit source is copied byte for byte into its sRGB variant, other formats are decoded to linear by the conversion shader and written through an sRGB render target. `-gasvrclassiccolor=1` (the launcher's Graphics → VR rendering → Classic colors) keeps the earlier choice. bridge.log names the path once per format: `Eye colour: source format=… swapchain format=… copy|decode_to_srgb|convert`.

Texture filtering (`texture_filtering.cpp`, the launcher's Graphics → VR rendering → Texture filtering): `ID3D11Device::CreateSamplerState` (vtable slot 23) is hooked in headset sessions. The game makes most world-surface samplers anisotropic at 4x (its `<anisotropic min="4" max="16" />`) and one with a -1 mip LOD bias. `-gasvrtexturefilter=1` raises every mip-filtered sampler to 16x and clears a negative bias; `-gasvrtexturefilter=2` also adds +0.5 bias. Comparison, minimum/maximum and point samplers are untouched. Diagnostic logging lists each distinct sampler once (`Sampler N filter=… aniso=… bias=… lod=…`). `capture/xrsim_play.py --benchmark --route route_3` runs the benchmark race on another San Francisco route; pass `--game-arg=-gasvreyesize=WxH` for a real headset's eye size (the harness otherwise renders 400x600 eyes).

Settings → Diagnostics (`performance_display.cpp`, as GRID2VR): `-gasvrperformance=1` adds a 640 x 64 quad layer in VIEW space over the eye images (or the seated screen), 1.5 m ahead and below centre, nearer than the HUD plane at most 95% of its distance, redrawn once a second without waiting on its swapchain: `FPS <frames sent in the last second>/<display rate>  GPU <percent>`. GPU usage is the busiest engine of the game's adapter, all processes included, from the Windows `GPU Engine` counters on a worker thread; N/A when unavailable. `-gasvrdiagnostics=1` logs `Frame rate second fps=… display_hz=… gpu=…` each second and samples native frames every 300th frame instead of every 1800th; the launcher adds a `Diagnostics:` line to `supervisor.log`. Test only: `-gasvrperfdump=1` saves the panel's first picture as `performance-display.bmp` in the session folder (`python capture/xrsim_play.py --benchmark --game-arg=-gasvrperformance=1 --game-arg=-gasvrperfdump=1`; xr-sim's captures show the composited panel).

Force feedback (`-gasvrffb=STRENGTH,WEIGHT,VIBRATION`, the launcher's Controls → Driving option, `force_feedback.cpp`, GRID2VR's shaping): GRID Autosport, like GRID 2, drives a wheel through `DINPUT8!DirectInput8Create` with a DirectInput constant-force effect whose magnitude carries the aligning torque, kerbs, surface and impacts already mixed. The bridge routes that import from DllMain, then patches dinput8's own method tables as the game uses them: `IDirectInput8::CreateDevice` (slot 3), each device's `CreateEffect` (slot 18) and each constant-force effect's `SetParameters` (slot 6), every detour looking its original up by the caller's table. Only the game's calls are shaped, on a private copy of its `DIEFFECT`: a 3 Hz one-pole low-pass splits the magnitude into weight (slow) and vibration (the rest), and the wheel gets strength x (weight x slow + vibration x rest), clamped to +/-10000. Other effect kinds pass through unchanged, and 100/100/100 hooks nothing. The bridge log names the game's DirectInput, devices and effects, and every 18000th shaped update reports peak input / output.

Head tracking can be checked in the cockpit with scripted xr-sim poses during the game's own benchmark race: `python capture/xrsim_play.py --benchmark --cycle-camera --race-seconds 90 --no-focus-loss --seconds 220 --shots "" --script capture/poses_cockpit.json` (the cycling camera shows the driver cockpit around race second 90; without `--cycle-camera` it is the chase camera). Each step's `shot` is what the simulated headset shows; `capture/poses_recenter.json` checks a runtime recenter. When the runtime recenters LOCAL (`REFERENCE_SPACE_CHANGE_PENDING`, e.g. holding the Quest's Oculus button), the bridge re-places the seated screen and recenters the seat, as the game's own recenter does. xr-sim's compositor does not apply the LOCAL origin to projection layers, so after a simulated recenter its captures show the correct render rotated by the recenter angle.

The game sizes each eye from the per-eye size the bridge reports at renderer setup; it no longer follows the desktop window. The launcher reads the headset's OpenXR recommended size from its runtime check before every VR launch, applies **VR render scale** (Graphics → VR rendering, 50–300%, limited to 8192 px per eye because both eyes share one texture) and passes `-gasvreyesize=WIDTHxHEIGHT`. Without it the game keeps its legacy eye size (half the 800×600 window per eye here). `capture/xrsim_play.py --game-arg=-gasvreyesize=3072x3264` reproduces a Quest 3 at 100%; the bridge log records the request and the resulting eye target. While the seated screen is shown (startup and loading), the bridge gives the game a centred field of view with the headset's total width and height, so the off-centre lenses do not push the loading cards past the eye image, and shows that image at its field-of-view aspect. (The back buffer during loading holds only the generic logo splash.)

The launcher's recenter shortcut (Controls → VR, default F10 as in GRID2VR) reaches the bridge as `-gasvrrecenterkey=VK -gasvrrecentermods=MASK` (1 Ctrl, 2 Alt, 4 Shift). The bridge matches it in the game window's messages with exactly those modifiers (physical key state), consumes it, recenters the seat and places the seated screen in front again; the game's own F11 recenter keeps working. `-gasvrkeephorizon=0` (Keep horizon level off) also aligns pitch and roll to the head. `capture/poses_recenter_key.json` checks both with a posted F10.

Shortly after the title scene appears, the game stops calling the HMD frame path and draws the menus with its own uncapped swap-chain `Present`. While that lasts, the bridge ends the abandoned HMD frame and shows each presented back buffer on the seated screen, paced by `xrWaitFrame`. The HMD path takes over again at the next native BeginFrame.

The runner restores the stock executable and removes its session files after the game exits. If the runner was interrupted, close Autosport and run `python bridge/run.py --restore`. Keep the run directory until restoration succeeds. Steam game executables and backups are local test data and should be excluded from release packages.

A play session may carry its own Practice / Race file: with `-gasvrplay=<token>` the bridge accepts exactly `-benchmarkAttract GASVR_<token>.xml` (and no other `-benchmark` argument), logged as `practiceSession=1`. The launcher stages that file and the guarded `system/flow.bin` with the session. Without a headset: `GRIDAutosportVR.exe --write-session --game-dir <game> --settings practice.json practice.xml`, then `python capture/xrsim_play.py --session practice.xml --flow <guarded flow.bin> --no-focus-loss --seconds 150 --script capture/poses_race_progress.json`; the harness stages and removes the session file and restores the stock flow. Launcher driving bindings can be checked the same way: `GRIDAutosportVR.exe --write-input-maps --game-dir <game> --controls <driving-controls.json> <out>` writes the input presets a launch would stage, and `--stage input/xinput_pad_0.xml=<out>/input/xinput_pad_0.xml` (repeatable) swaps each one in for the run with a verified backup and restore. With Menu Select bound to the pad's Y button, the game showed Y as Select and accepted only Y, before and after loading the profile (12 Nov).

The game reads the keyboard through Raw Input and DirectInput and ignores input while its window is not in the foreground, so keys the harness posts to the window (`"key"` steps) reach only the bridge's own handler (the recenter key). For game input without taking the desktop's focus, `-gasvrtestpad=1` (test only; the launcher never passes it) makes controller 0 a virtual gamepad and reports the game's window as the foreground one. `capture/xrsim_play.py` adds the flag when a script has `"pad"` steps, e.g. `{"at": 4, "pad": "START", "hold": 0.4}` or `"A"`, `"DOWN"`, `"LB+RB"`: the harness writes the buttons to `pad.txt` in the session folder and the bridge reports them. On the title screen Start and A work through the menus; in a Practice / Race session the game reads the pad only once the bridge has claimed it (`--game-arg=-gasvrdevice=xinput_pad`), and then Start opens the game's pause menu (Restart, Replay, Rules, Difficulty, Quit). In-game Quit there ends the run through the benchmark worker's terminal `ExitProcess(0)` (RVA 685011 / 6851F4), which skipped the OpenXR shutdown (xr-sim fail-fasts on that: its threads are still joinable at exit); headset Practice / Race now takes the capture benchmark's path, a game window close, so the game's own teardown releases the session (checked on xr-sim, 14 Nov: Quit exits with 0 after a complete shutdown handshake, and Restart reloads the race).

With `-gasvrcockpit=1` (the launcher's **Camera → Start in the cockpit view**, on by default) a headset Practice / Race session starts in the car's `head-cam` view, the driver cockpit that every shipped car defines. When the race scene begins the game asks its vehicle view manager for the player's view by name (RVA 2D4AE5: the saved `current_camera`, which benchmark and attract sessions replace with `chase_close`); the bridge answers that one request with `head-cam`, on the game's own thread, and keeps the game's choice for a car without it. The change-camera button still cycles views. Normal play keeps the camera the player last used.

Practice / Race never shows the Press Start screen, whose update (RVA 196530) makes the device that pressed Start player 0's controller: it calls Input2 RVA 78E4B0 (`__thiscall`, the player's map from `[[players+0x44]+0xC]`, a 12-byte `{backend, family, index}` device record) at RVA 19669E. Without it the player's map stays keyboard-only, so wheel and pad bindings (and force feedback) do nothing in a direct session. The launcher passes `-gasvrdevice=FAMILY[,FAMILY...]` for Practice / Race only (the DirectInput product GUIDs its steering is bound to, then `xinput_pad`); when the race's StateLoading exits (the call at RVA 243FC9, with the state in ESI), `device_claim.cpp` lists the game's devices through its own enumerator (RVA 97DAB0 on Input2+0x84, released by RVA 8E1C0), interns the families with RVA 98AE00 and makes that same native bind once, for the first family connected. These three helpers are byte for byte GRID 2's, as used by GRID2VR's device claim. The bridge log records every game device and the bind's result (0x58: the game found no preset for the device).

On the seated screen (startup, loading, intro shots, pause) the game lays its 2D frontend out for the eye texture's pixel aspect, about 0.94:1 on a Quest 3, while the screen shows the frame at the flat field of view's aspect (at least 16:9). Every frontend draw except the race HUD therefore has its clip x scaled by the ratio of the two in the stereo pass (`updateUiCamera`; the native draw restores the matrix after the batch), so a 16:9 layout lands whole in the eye image and the screen stretches it back. The bridge log names each scaled draw once. This fits the loading cards (checked on xr-sim, 13 Nov); the pre-race intro's left info panel is still cut at its left edge and does not follow further squeezing (ProJict 60b6f461).

The launcher's controller / wheel recenter button (Controls → VR) is watched by the launcher itself while the game runs (`launcher/DeviceRecenter.cs`, nonexclusive input); each press drops `recenter.request` into the play session folder, which the bridge checks every 100 ms, deletes and treats as the recenter shortcut.

VR runtime choice (launcher Settings → VR runtime, as GRID2VR): with VDXR or SteamVR chosen, the session folder's `openxr-runtime.txt` holds the kind and the runtime manifest path (`virtualdesktop-openxr-32.json` or `steamxr_win32.json`). Steam does not pass the launcher's environment to the game, so `initXR` sets `XR_RUNTIME_JSON` in the game process only around `xrCreateInstance`, restores it, and refuses a runtime whose name does not match (VirtualDesktopXR, SteamVR/...). Without the file the system's runtime is used. `capture/xrsim_play.py --runtime-choice VDXR[:broken]` exercises both paths with a renamed xr-sim manifest.

Release checks (`tools/release_check.py`): Launch VR through Steam on xr-sim, without a headset. The session supervisor gets `GASVR_TEST_VDXR_MANIFEST`, a copy of xr-sim's manifest named `virtualdesktop-openxr-32.json`, which it writes as the VDXR runtime choice; the bridge accepts the runtime name `xr-sim` for either choice. It checks the launch steps, a graphics preset applied and restored, the frame-rate summary, an interrupted session with `--restore-play`, Normal play with Game settings, and Diagnostic logging with the performance display (the system summary, the panel redrawn, a frame-rate and GPU line each second), and restores the player's launcher and game settings files byte for byte.

Launch progress (launcher `VrLaunchStatus.cs`): the session supervisor writes each step to `vr-launch.json` in the launcher's data folder, and once the game runs it follows `bridge.log`: `native renderer configured`, `OpenXR runtime`, the XR session states up to the first `FOCUSED` (VR running). When the renderer fails, `AutosportBeginViews` logs `VR failed: <reason>` once (later frames only repeat `reinitialize_bridge_after_failure`), and the progress window shows that reason.

Frame rate (launcher Graphics → Last VR session): `xrWaitFrame` logs the runtime's display period (`XR display period=… display_hz=…`, again only after a change of more than 1%). Each projection (stereo) submission counts toward one-second frame-rate windows; a seated-screen frame or a gap over 250 ms ends the window, so menus, loading, pauses and videos are left out. At shutdown the bridge writes `performance.json` to the session folder (`{"schema":1,"displayHz":…,"windows":…,"fps":{"p50":…,"p5":…,"min":…},"dips":{"share":…}}`, dips being windows under 95% of the display rate) and logs `Frame rate windows=…`. The launcher keeps it with the session's settings as `last-vr-performance.json`.

Graphics presets (launcher `GraphicsCatalog.cs`, data from `tools/build_graphics_catalog.py`): the game reads its quality from `Documents\My Games\GRID Autosport\hardwaresettings\hardware_settings_config.xml`, for Practice and Race too. With a preset other than Game settings, the play session backs that file up in the session folder, writes the preset's attributes and multisampling into it under the play lease, and restores the backup after the game exits (the game rewrites the file on exit; a changed copy is kept as `session-hardware-settings.xml`).

OpenXR layer bypass (GitHub issue #1, launcher `VrApiLayers.cs`, ported from GRID2VR): an implicit API layer with no working 32-bit library makes the 32-bit loader fail `xrCreateInstance` with -32 ("Failed loading layer information") when no other implicit layer loads. The launcher's headset check runs with `XR_LOADER_DEBUG=warn`, so the loader names the layer; after the player agrees, the session folder's `openxr-layer-bypass.txt` lists that layer's own disable switch (`DISABLE_XR_...` or `DISABLE_OPENXR_...`, one per line, at most 16). `initXR` sets each to 1 only around `xrCreateInstance`, together with `XR_RUNTIME_JSON`, then restores the previous values, and refuses a malformed file. `capture/xrsim_play.py --layer-bypass DISABLE_...` writes the file.

Desktop mirror: the window shows the eye image. When the eye target and the back buffer differ in size (always in headset play: the launcher passes the headset's eye size), `AutosportDrawMirror` draws the last submitted left eye (or seated-screen frame) from the resolved snapshot, scaled and centre-cropped to the window, with a linear sampler on the private deferred context; equal sizes keep the plain copy. `-gasvrmirrordump=1` (test only) writes the mirrored back buffer once to `mirror.raw` in the session folder.

Seat adjustment (`seat.cpp`, GRID2VR's Controls → Seat and Tab panel): per-car offsets in millimetres right / up / forward in `<data>\seat-adjustments.txt` ("car right up forward"), shared with the launcher. At each race start (`raceStartView`) the bridge records the vehicle view manager's head-cam index and its car: the head-cam view (manager view getter VA C0DEE0) has an owner at +0x84 whose +8 is the car's model name (e.g. `sls`). The offset is added to the head pose (x right, y up, -z forward in the recentered seated space) only while that head-cam is the live view (manager +0x81C) in a race scene, not on the seated screen. The panel key (default Tab; `-gasvrseatkeys=PANEL,UP,DOWN,BACK,FORWARD` virtual-key codes from the launcher's Seat keys, default `9,38,40,37,39`) opens the seat panel in the cockpit: GRID2VR's 768x1024 picture (`seat_panel.cpp`, GDI+: seat side view, red arrows, offsets, keys; car names from `<data>\car-names.txt`, written by the launcher at each VR launch) on a 0.6 x 0.8 m OpenXR quad 1 m ahead at eye level. Up / down change height, back / forward depth, with Shift sideways, 1 cm a press; Backspace resets, Enter or the panel key saves, Esc cancels. While it is open those keys, Shift, Enter, Esc and Backspace are withheld from the game (window key messages, Raw Input `GetRawInputData` and `GetAsyncKeyState` imports). `capture/xrsim_play.py` script steps can post TAB, BACK, the arrows and PGUP / PGDN.

Nearby opponent LOD (`opponent_lod.cpp`, as GRID2VR and DiRT2VR): the game picks each car's level of detail for the main view only, so an opponent beside or behind drops to its lowest model in the headset. The LOD selector (VA 9FDBD0) writes each car record's selected LOD (record +0xFC; records at manager +0x10FC, stride 0x18A0, count +0x19BB4) and then calls the apply (VA 9FDB40); the bridge takes that call (RVA 5FE647) and first raises every opponent within 30 native units of the focus car (manager helper VA 670B00; car position +0x60) to LOD 1, keeping it until 40 units. LOD 1 is the game's own top level for opponents: the selector's budget table (manager +0x19CB4, five counts per profile) allows LOD 0 for one car only, the focus car's own model, whose player-only parts showed under an opponent Ford Focus ST. A car whose best level (car +0x124) is lower in detail keeps its best. The car's SetLod (VA B33A80) falls back to a loaded model by itself. VR race scenes only; `-gasvropponentlod=0` keeps the native choice for comparisons. The log reports the first raise and a count every 3600 passes.

Videos over a race scene: starting a career plays `rush01.bk2` through the frontend's video composite once the first race has loaded (no video state is entered). The video reaches only the back buffer: the desktop window plays it while the eye texture keeps the race's first frame (seen in the headset on the PC4090 test). From the Bink open in a scene until its close the bridge shows the back buffer on the seated screen, as for the startup videos, and keeps drawing the frontend passes that Intro shots in 3D otherwise skip (`Video over the race scene` log lines; `-gasvrscenevideosource=eye` keeps the eye texture, for comparisons). Not reproduced on xr-sim: the attract demo race, which opens the same video, did not start reliably there.

Career intro video states: StateDisciplineIntroVideo (a career or new discipline) and StateDLCChampIntroVideo play after the race scene has loaded, and the headset otherwise kept the race's first frame. The bridge replaces slots 3 (enter) and 12 (leave) of their vtables (RVA CFD178 and CFD1C0; only when the entries hold the expected stock functions) and, while one is active, shows the back buffer on the seated screen as for the startup videos (`Intro video ...` lines in the session log).

Cockpit textures (`cockpit_textures.cpp`, GRID2VR's focus cockpit): each car's cockpit atlas is `<car>_cabin.tga` in `cars/models/<car>/livery_user/textures_low/<car>_tex_low_user.pssg`, 512x512 DXT5 whose alpha is a material mask. `tools/Export-CockpitTextures.ps1` exports all 83 read-only. The game uploads it as BC3 with 8 mips and its stock pixels as initial data, so the SHA-256 of those 8 mips identifies the car. With `-gasvrcockpittextures=observe` the bridge hooks the game device's CreateTexture2D and CreateShaderResourceView and logs texture shapes and atlas hashes to `cockpit-textures.log`; `=replace:<version>` (passed by the launcher when Graphics → Cockpit textures is on and the pack verifies) gives a recognised atlas's view a view of `<data>\addons\cockpit-textures\<version>\<car>.dds` (square DXT5, full mip chain; `<data>` is the launcher's data folder, two levels above the session folder), listed in `catalog.txt` there with its source and file hashes; a file whose hash does not match is skipped and the stock atlas stays. `tools/build_cockpit_texture_pack.py` builds the pack from redrawn colour atlases (the GRID2VR method: Codex's built-in image generation, one edit per stock atlas), matched to the stock atlas's brightness and joined with the stock alpha, 2048 square with 12 mips.
