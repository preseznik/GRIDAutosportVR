# GRID Autosport VR launcher

C# WinForms launcher (.NET 10, x64) ported from GRID2VR's launcher shell: header with logo, channel and **?** (F1), selectable status and notice lines, owner-drawn tabs of collapsible sections (remembered in `launcher-window.json`), a responsive two/one-column layout, Modern/Classic themes that follow Windows light/dark and high contrast, and the footer **Launch | Launch VR | Save settings | Restore original files | Open logs**.

Choices are kept by **Save settings** or a launch in `%LOCALAPPDATA%\GRIDAutosportVR\settings.json` (`hudFollowView`, `modernInterface`, `vrRenderScale`; other keys are preserved). **Graphics → VR HUD** keeps `hudShow`, `hudDial`, `hudMinimap`, `hudCounters`, `hudPositions` (passed as the `-gasvrhudparts` mask: 1 entire HUD, 2 dial, 4 minimap, 8 counters, 16 position info) and `hudDistance` (1–20 m in 0.5 m steps, passed in centimetres as `-gasvrhuddistance`); **Graphics → VR screen** keeps `screenDistance` (1.5–6 m in 0.5 m steps, default 1.5 m, passed in centimetres as `-gasvrscreendistance`) and `intro3d` (pre-race intro shots in 3D, `-gasvrintro3d=1`, off by default). **Controls → Driving** opens the driving bindings ported from GRID2VR (`DrivingControls*.cs`, `DrivingInput*.cs`; kept in `driving-controls.json`, profiles in `driving-profiles\`) and the live input view; controllers and wheels are read through `driving_input.dll` (`tools/driving-input`, DirectInput + XInput, x64, shared with GRID2VR and DiRT3VR). On a VR launch `SessionInputMaps` rewrites, for each bound device family, the game's own preset for it (`keyboard.xml` and `keyboard_azerty.xml`, `xinput_pad_0/1.xml`, a wheel's own preset by its product GUID in `device_type` / `device_type_N`) with the bound actions replaced; a DirectInput device without a preset gets one made from `dinput_default.xml`, written over the shipped preset of an old wheel (`HostPresets`: MOMO Racing, Driving Force EX, Driving Force Pro, RGT FFB Pro, F430 FFB, G25, in that order; never a bound device's own), which keeps its file and map name and takes the device's product GUID as `device_type`. `input/paths.xml` is never changed: a preset under a file name the game does not ship made every career save fail before any file was written ("Data save failed", then "autosave will be disabled"), and the game's fallback `di_default` map does not answer the menus on a wheel. In that preset every axis is removed from the Menu, Fe, Replay, Spectator and Youtube actions (`dinput_default.xml` is a gamepad's and puts the menus on X and Y, a wheel's steering and a pedal, so a pedal at rest held Menu Up or Down; the game's own wheel presets keep menus on the D-pad and buttons). Assigning an input to an in-race action removes it from any other in-race action on that device (the two halves of an axis share it), and at staging a Radio or Instant Replay binding on an input a driving action also uses is left out. In-race actions the launcher does not bind (everything but the Menu, Fe, Replay, Spectator and Youtube actions) lose the inputs it binds for that device, as the game's own remap screen does (`dinput_default.xml` gives Radio TeamMate Drop/Push and Clutch the buttons that are a G29's shift paddles); look actions (Look Left/Right/Up/Down/Back, Fe View Tweak) also lose every axis on a DirectInput device (the game's defaults put them on Z/Rz, where wheels have pedals); in a two-device preset (`device_type_0`/`device_type_1`) a binding gets `restricted_device` and the other device's inputs for that action stay. The files are staged under the play lease with SHA-256 backups and restored after the session; one changed independently is preserved with the lease. A Normal VR launch with staged bindings passes the bound controllers as `-gasvrdevice` (`NormalClaim`: no keyboard, no guessed controller): the save profile's controls replace the presets after Press Start, so the bridge binds the session preset again after each loading screen and keeps the profile's own controls in the game's saves. `--write-input-maps --game-dir FOLDER --controls FILE OUTPUT` writes the presets the next launch would stage, without staging anything. **Graphics → Desktop** keeps `desktopVSync` (default true), `desktopMsaa` (`game`, `off`, `2xmsaa`, `4xmsaa`, `8xmsaa`) and `desktopDisplay` (`game`, `fullscreen`, `window`); a desktop **Launch** (Normal or Practice / Race) writes them into the game's `hardware_settings_config.xml` (`resolution@vsync`, `@multisampling`, `@fullscreen`) while the game is closed, and a VR session's staged copy always has `vsync="0"`. **Graphics → VR rendering** sets VR render scale relative to the headset's OpenXR recommended per-eye size; **Refresh headset** and every VR launch read that size from the probe and keep it in `headset.json`, and the launch passes the scaled size to the bridge as `-gasvreyesize`. **Controls → VR** sets the recenter key (`recenterKey`/`recenterModifiers`, default F10; system shortcuts are refused) and **Keep horizon level** (`keepHorizonLevel`), passed as `-gasvrrecenterkey`, `-gasvrrecentermods` and `-gasvrkeephorizon`. **Launch VR** re-runs the launcher as `--play-vr --game-dir FOLDER`: it checks the 32-bit OpenXR runtime, stages the verified VR executable and bridge under a recovery lease, starts the game through Steam and restores the stock files when it exits. **Launcher → Session** chooses the launch mode (`launchMode`: Normal, Practice or Race), `car`, `track`, `laps`, `opponents`, `opponentCars` (same, class or mixed) and `vrCockpit` (start in the cockpit view, passed as `-gasvrcockpit=1`) from the installed `cars/models` and `tracks/locations` folders. For Practice and Race, `--play-vr` writes the session file `GASVR_<session>.xml` (benchmark-style: the player on grid 0, opponents behind with the example benchmark's driver presets) into the game folder, swaps `system/flow.bin` for the guarded flow and adds `-benchmarkAttract GASVR_<session>.xml`, all under the same recovery lease, and restores both afterwards. The guarded flow is the stock file with the three `attract_mode_chosen` decisions sent to the normal player start (research: `tools/practice_flow.py`); the launcher makes it on the player's PC from their own stock file with a pinned 25-byte patch (`PracticeFlow`), checking the input and output hashes. Car names and disciplines come from a table in `RaceSession.cs`; disciplines only group Same discipline opponents. `--write-session --game-dir FOLDER [--settings FILE] OUTPUT` writes the session file the next launch would use, without staging anything. Practice and Race run on the game's benchmark mode, which ignores the pause button; **End session** (shown beside Launch VR while a session runs, also `--end-session --game-dir FOLDER`) asks the game in that folder to close as its window's close button does, ends it after 15 s if it has not, and the session supervisor then restores the files. `--restore-play --game-dir FOLDER` restores an interrupted session and `--inspect` prints the detected installation as JSON.

Build and check without a headset or game launch:

```powershell
dotnet build launcher\GRIDAutosportVR.csproj -c Release
launcher\bin\Release\net10.0-windows\win-x64\GRIDAutosportVR.exe --self-test artifacts\launcher-selftest
pwsh -File capture\verify_play_session.ps1 -LauncherAssembly launcher\bin\Release\net10.0-windows\win-x64\GRIDAutosportVR.dll -StockAvx "<Steam>\steamapps\common\GRID Autosport\GRIDAutosport_avx.exe" -Bridge artifacts\bridge-build\Release\gasxr.dll
dotnet publish launcher\GRIDAutosportVR.csproj -c Release -o artifacts\launcher
```

The self-test uses a temporary data folder and renders every tab, Modern and Classic, at 900 and 600 px to `launcher-*.png` from an off-screen window that never takes focus. With `GASVR_TEST_GAME` set to an installed game folder, the self-test also checks the real catalog and flow patch and stages and restores a Practice session on a temporary copy of the AVX and `flow.bin` (the installation itself is only read). `verify_play_session.ps1` exercises staging and recovery on a copy of the stock executable in a temporary Steam library. The single-file publish places `probe\AutosportXRProbe.exe` and `renderer\gasxr.dll` beside the launcher. Release packages come from `tools\Package.ps1` (see the root README); the installer (`installer\GRIDAutosportVR.iss`) puts the package in `<game>\GRIDAutosportVR` and uses `--discover`, `--check-install` and `--check-uninstall` to suggest the Steam folder and to refuse while the game runs or a VR session's files are staged.

**Profile** (career profiles, `Profiles.cs`, `ProfilePanel.cs`, ported from GRID2VR): separate careers in `%LOCALAPPDATA%\GRIDAutosportVR\profiles\<id>\` (`profile.json`: schema, id, name of 1–24 letters or digits, kind `fresh` or `copied`, created time, Steam account; `remote\`: the game's Steam Cloud files, at most 64 files and 64 MiB, no links), selected in `profile-selection.json` (`current` or an id; missing means `current`, the game's normal Steam career in `Steam\userdata\<account>\255220\remote`, never written by the launcher). Create (fresh, or a byte-for-byte copy of the current career), select and delete need the game closed and no session running; a profile belongs to the Steam account that made it. Every session for a selected profile writes `profile-storage.request` (`GASVR_PROFILE_STORAGE_V1`, the profile's `remote` folder, its id and the Steam account) into the session folder and checks the bridge's `profile-storage.json` receipt when the game exits: `refused` (the game was stopped before it read any save) or write failures are reported as the session's error. With a profile, desktop **Launch** with Normal runs through the session supervisor too (`--play-desktop`, `-gasvrmode=desktop` without a session file). The 2014 build uses the current career only. Each career's **Progress** (`CareerSaves.cs`) is the label of its load-menu directory `savegame@profile0#QKRHMYXE` ("… Career Races: N, Online Races: M"), checked with the game's own checksum. The directory is encrypted with the game's save codec, so the launcher runs that codec from the installed, verified `GRIDAutosport_avx.exe` under the Unicorn emulator (`career\unicorn.dll`, 2.1.4 from the pinned wheel, staged by `tools/Stage-CareerRuntime.ps1`, with its GPLv2 source in `licenses\Unicorn`); the addresses and a Python reference reader are in `tools/career_profile/stock_save.py`. Decoding runs in a child launcher (`--read-careers REQUEST`) started with Control Flow Guard and CET shadow stacks off, because Unicorn's longjmp fails fast under either; the launcher itself keeps both on. **100% complete career** (`CareerCompletion.cs`, `CareerStart.Completed`, profile kind `completed`) copies the current career into the new profile's staging folder and completes it there in a child launcher (`--complete-career REQUEST`), before the profile exists. Only fixed-size fields of the RaceHistory component change, in both career files: every cup (40 slots of 108 bytes) and championship (50 slots of 80 bytes) record gets best position 0, times completed, wins and wins with the Ravenwest team at least 1 (championship word 16, cup word 21; a championship's word 19, the Ravenwest season, at least 1), and the five disciplines' records 9,999,999 XP (database `career_xp_level` 12) with seasons for their level 10–12 milestones (words 32–34). The files are re-framed (raw deflate + SHA-256; the progress file fills whole 16-byte cipher blocks through a stored final block, the settings file is padded with 0xBE to the shared 256 KiB), encoded with the game's own writer (`0xd753d0`, directory `0xd7b240`) and read back before they are kept. The layout and a Python reference are in `tools/career_profile/complete_career.py`.
